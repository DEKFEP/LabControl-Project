LabControl — PENDIENTES Y LIMITACIONES CONOCIDAS
================================================

Documento de trabajo interno. Solo contiene lo que falta por hacer o sigue limitando
el despliegue actual. Versión del proyecto: 4.9.0. Los hallazgos del informe y su
prioridad están en INFORME-AUDITORIA-4.8.txt (sección 8; nombre histórico de la
auditoría, realizada sobre 4.8). La documentación de uso está en README.md.


1. INTEGRACIONES EXTERNAS PENDIENTES
------------------------------------
Correo de recuperación (Resend)
  El flujo está construido y probado, pero sin proveedor no se envía ningún correo.
  El enlace ya no se imprime en los logs (M-07): en producción RESEND_API_KEY es
  obligatoria y el token solo se guarda hasheado en la base (B-02).
  Falta:
    1. Crear la cuenta en resend.com y verificar un dominio propio (o usar
       onboarding@resend.dev, que solo entrega a la casilla indicada).
    2. Definir RESEND_API_KEY y RESEND_FROM en el servicio del backend.
    3. Configurar SPF y DKIM si se usa el dominio del establecimiento.
    4. Probar solicitud, recepción, enlace y cambio de contraseña.

Inicio de sesión con Google
  El botón existe, pero no autentica: falta el cliente OAuth y las rutas.
  Falta:
    1. Crear el cliente OAuth en Google Cloud Console y definir GOOGLE_CLIENT_ID
       y GOOGLE_CLIENT_SECRET.
    2. Instalar la librería OAuth en website/backend.
    3. Implementar GET /api/auth/google y GET /api/auth/google/callback.
    4. Decidir qué correos se admiten y qué rol heredan; conectar el botón.
    5. Mantener el segundo factor en el inicio de sesión del administrador.

Copia externa en Cloudflare R2 (opcional)
  No es requisito para usar la página: sin R2 todo funciona igual. Solo añade una
  copia que sobrevive si se borra el volumen o se pierde la cuenta de Railway.
  El código ya está listo y no se activa mientras LC_BACKUP_AUTO no esté definido.
  Falta, cuando se decida:
    1. Crear el bucket privado labcontrol-backups y un token con Object Read & Write
       limitado a ese bucket.
    2. Añadir la regla de ciclo de vida de 90 días sobre el prefijo labcontrol/.
    3. Cargar en Railway LC_BACKUP_AUTO=1, LC_BACKUP_S3_URI, LC_BACKUP_S3_ENDPOINT,
       LC_BACKUP_S3_REGION=auto, AWS_ACCESS_KEY_ID y AWS_SECRET_ACCESS_KEY.
    4. Redesplegar y comprobar el objeto en R2.
  Coste esperado: dentro del plan gratuito de R2.


2. RESPALDOS
------------
Backups del volumen de Railway (línea base, requiere plan de pago)
  El backend corre hoy en el plan Free, que no incluye backups del volumen
  (límite maxBackupsCount = 0). Para activarlos hace falta un plan de pago que
  los incluya; comprobar en el panel antes de contratarlo.
  Panel: https://railway.com/project/558eff01-f251-4071-a324-140a97223b34/service/96216807-0dc0-4da3-bf85-7e7d83a233f7?environmentId=74f2e700-73d7-4f4f-ba15-5d5224f0fe25
  Guía:  https://docs.railway.com/volumes/backups
  Pasos, una vez en un plan que los incluya:
    1. Servicio del backend → Settings → Backups.
    2. Activar Daily (6 días), Weekly (27 días) y Monthly (89 días).
    3. Lanzar un backup manual y comprobar que aparece.
  RPO: 24 h. RTO: minutos.
  Límites: si se borra el volumen, Railway borra también sus backups; restaurar
  un punto descarta los backups más nuevos. No cubre borrar el proyecto, la cuenta
  ni una caída prolongada del proveedor.
  Mientras el servicio siga en Free, la copia disponible es la descarga manual de
  Configuración → Respaldos (y la copia externa en R2 si se activa).

Probar una restauración en staging
  Antes de restaurar, descargar el estado actual y verificar la copia elegida.
  Después del redespliegue, ejecutar PRAGMA integrity_check y revisar usuarios,
  agenda y equipos. Repetir al menos una vez al trimestre.
  Responsable: administrador del sistema, con apoyo del encargado de informática.


3. DESPLIEGUE Y SEGURIDAD PENDIENTES
------------------------------------
  0. Decidir el plan de Railway. El backend ya está activo en el plan Free
     ($0/mes, $1 de uso incluido; consumo estimado actual ~$0,13/mes). Ese plan
     no incluye backups automáticos del volumen ni dominio propio, y detiene el
     servicio si se agota el crédito mensual. Para backups o dominio propio hay
     que pasar a un plan de pago con método de pago desde
     https://railway.com/account/billing.
  1. Definir LC_PROXY_SECRET en Railway y en el proyecto de Cloudflare Pages.
  2. Definir LC_SALUD_TOKEN en Railway y como secreto del repositorio
     (gh secret set LC_SALUD_TOKEN).
  3. Definir LC_PUBLIC_URL con la URL pública https del sitio
     (https://insuco-labcontrol.pages.dev o el dominio propio), no la URL de
     Railway: se usa para las cookies Secure, el CORS y los enlaces de correo.
  4. Definir API_ORIGIN en Pages apuntando a la API de Railway.
  5. Rotar la contraseña del administrador INSUCO, revocar sus refresh tokens y
     revisar la auditoría por accesos antiguos con esa cuenta.
  6. Activar 2FA en cada cuenta admin. Hoy es por usuario, no hay bloqueo global:
     si se quiere obligatorio, hay que añadir esa comprobación al login.
  7. Acercar el backend a Chile: recrear el servicio con su volumen en una región
     próxima y volver a apuntar API_ORIGIN. Es manual, desde el panel.
  8. Conectar el dominio propio: agregar el dominio a Cloudflare, cambiar los
     servidores de nombres y añadirlo como dominio personalizado en Pages.
     El plan Free de Railway no admite dominios propios; si se quiere usar el
     dominio también en la API, primero hay que pasar a un plan de pago.
  9. Renovar RAILWAY_API_TOKEN en GitHub: el actual no autoriza el proyecto
     (el run 42421136498 falló con Unauthorized). Crear un token de cuenta en
     https://railway.com/account/tokens y ejecutar:
       gh secret set RAILWAY_API_TOKEN -R DEKFEP/LabControl-Project
     Mientras tanto, la API se despliega a mano desde la raíz del proyecto:
       npx @railway/cli@5 up website/backend --path-as-root --service api \
         --environment production --project 558eff01-f251-4071-a324-140a97223b34 -c

5. LIMITACIONES VIGENTES
------------------------
Avisos del sistema operativo
  Dependen del navegador; en algunos solo se ven con la aplicación abierta.

Modo sin conexión
  El service worker guarda el inventario de solo lectura. No se pueden crear ni
  modificar datos y no se guarda información personal. La caché de la API se
  descarta al iniciar sesión, al verificar el segundo factor y ante cualquier
  401 (M-09), así que una sesión caducada ya no deja los datos del usuario
  anterior visibles para el siguiente.

código; el detalle está en INFORME-AUDITORIA-4.8.txt, secciones 8.1 a 8.4.
Lo que sigue en este documento son decisiones y acciones de infraestructura:
proveedores externos, backups en el panel, rotación de credenciales y la
publicación del cambio para que el subdominio muestre las URL limpias.
