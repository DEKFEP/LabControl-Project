--------------------------------------------------------------------------------
 0. RESUMEN EJECUTIVO
--------------------------------------------------------------------------------

El proyecto presenta una base de seguridad sólida y muy por encima de la media
para un sistema escolar. No se encontraron vulnerabilidades críticas explotables
de forma remota en el código actual: no hay RCE, ni bypass de autenticación, ni
inyección SQL evidente. El único hallazgo crítico es condicional: la credencial
demo histórica podría seguir activa en una base migrada y debe comprobarse en
la instancia real (C-01). Fuera de eso, los problemas importantes son de
INTEGRIDAD DE DATOS y CONFIABILIDAD, no de compromiso directo.

Los tres riesgos de integridad y confiabilidad que más deberían preocupar son:

  1. Los reportes de uso, disponibilidad, fallas e inventario se crean con DATOS
     INVENTADOS (números aleatorios y una falla ficticia) y se presentan como
     reales. Un directivo puede tomar decisiones con cifras falsas.
  2. La exportación de respaldo lee el archivo SQLite en vivo y puede producir
     una copia inconsistente o corrupta si coincide con una escritura.
  3. Hay errores funcionales visibles: el login con correo en mayúsculas falla,
     ciertos tipos de dato devuelven 500, se aceptan fechas imposibles como
     2027-02-31 y un reporte malformado rompe la vista del cliente.

ESTADO: los riesgos 1 y 2, el crítico condicional (credencial demo), los
errores funcionales M-01 a M-04 y todos los hallazgos M-05 a M-14 y B-01 a
B-12 ya están corregidos en el código (ver 8.1 a 8.4). Para durabilidad se
adopta como línea base los backups automáticos del
volumen de Railway (ver 6.4.1), que se activan en el panel. La copia fuera del
proveedor en R2 está implementada y documentada, pero queda pendiente por
decisión del establecimiento (ver 6.4.2 y PENDIENTES.txt).

--------------------------------------------------------------------------------
 Ubicación : PENDIENTES.txt; website/backend/db.js:813-816
 Tipo      : Credencial conocida / acceso no autorizado
 Estado    : CORREGIDO (04/11/2026). Ver 8.1.

 Descripción:
   Hasta la versión 4.1 se publicó la cuenta INSUCO / Insuco1336. El código
   actual guarda las contraseñas demo como hash bcrypt y la semilla demo está
   desactivada por defecto (LC_SEED_DEMO), lo cual es correcto. Sin embargo,
   cualquier base de datos creada antes de 4.1 y migrada hasta 4.8 conserva
   ese hash.

 Impacto:
   Si esa credencial sigue activa en producción, cualquiera que conozca el dato
   histórico entra como administrador: control total de usuarios, respaldos,
   configuración y datos personales. Sería un compromiso total del sistema.

 Verificación (ejecutar contra la instancia real, nunca contra la base local):

   curl -s -o /dev/null -w "%{http_code}\n" \
     -H "Content-Type: application/json" \
     -d '{"usuario":"INSUCO","password":"Insuco1336"}' \
     https://<host-real>/api/login

   Si devuelve 200, el hallazgo es crítico y confirmado.

 Recomendación:
   1. Probar la credencial en producción.
   2. Si funciona, cambiarla de inmediato y revocar todos los refresh tokens
      del usuario:
        UPDATE refresh_tokens SET revocado = 1 WHERE usuario_id = 'INSUCO';
   3. Revisar la auditoría (tabla auditoria / GET /api/auditoria) por accesos
      con esa cuenta desde fechas anteriores.
   4. Activar 2FA obligatorio para todas las cuentas admin.
   5. Añadir una comprobación al arranque que detecte hashes de contraseñas
      demo conocidas y avise (o bloquee) si están activos.

 A-01 · ALTO · Reportes con datos simulados presentados como reales
--------------------------------------------------------------------------------
 Ubicación : website/public/js/reportes.js:400
             website/public/js/reportes.js:430-442
             README.md:35
 Tipo      : Integridad de información / riesgo institucional
 Estado    : CORREGIDO (04/11/2026). Ver 8.1.

 Descripción:
   Al crear un reporte de tipo "uso", "disponibilidad", "fallas" o
   "inventario", el cliente genera los datos con generarDatosMock():

     labels: ["Lab 1","Lab 2","Lab 3","Lab 4","Lab 5"],
     valores: [70,65,50,15,85].map(v => v + Math.floor(Math.random()*15))
     ...
     return { fallas: [{ equipo:"PC-nuevo", lab:"Lab 1",
              descripcion:"Falla simulada", estado:"pendiente" }] };
     return { total:138, activos:134, enFalla:3, enMantencion:1 };

   Es decir: horas de uso y porcentajes de disponibilidad aleatorios, una falla
   ficticia y un inventario fijo. El README solo advierte que el control remoto
   está simulado, pero presenta los reportes como datos reales del sistema.

 Impacto:
   Las cifras quedan persistidas en la base y se exportan a CSV e impresión sin
   ninguna marca de "demostración". Se pueden usar para decisiones de compra,
   mantención o rendición de cuentas. Es el hallazgo de mayor riesgo práctico.

 Recomendación:
   Opción A (preferida): calcular los datos en el backend a partir de las tablas
   reales (agenda, equipos, reportes) al crear el reporte.
   Opción B (mínima): si aún no hay cálculo real, guardar
   datos: { demo: true } y mostrar un aviso visible en pantalla, CSV e impresión,
   y bloquear la exportación como si fuera oficial.

 Implementación sugerida (backend):

   // POST /api/reportes
   const datos = r.tipo === "otro" ? {} : calcularDatosReporte(r.tipo);
   // calcularDatosReporte consulta agenda/equipos y devuelve estructuras
   // validadas; nunca Math.random().

   Y en el cliente, eliminar generarDatosMock() y enviar solo { tipo, titulo,
   descripcion, fecha }.

 A-02 · ALTO · Exportación de respaldo potencialmente inconsistente
--------------------------------------------------------------------------------
 Ubicación : website/backend/server.js:1310-1323
             website/backend/db.js:60-65
 Tipo      : Pérdida de datos / corrupción de respaldo
 Estado    : CORREGIDO (04/11/2026). Ver 8.1.

 Descripción:
   El endpoint /api/backups/exportar transmite el archivo SQLite en vivo:

     const stream = fs.createReadStream(DB_PATH);
     stream.pipe(res);

   El comentario afirma que con journal_mode=DELETE la copia es consistente
   porque "cada transacción ya quedó volcada al archivo principal". Eso es
   incorrecto: en modo DELETE SQLite modifica el archivo principal en el mismo
   lugar durante la transacción; el journal permite revertir, pero no ofrece
   una instantánea legible concurrente.

 Impacto:
   Si la descarga coincide con una escritura (reserva, reporte, notificación,
   auditoría), el .db descargado puede contener páginas a medio escribir. El
   respaldo se ve válido (cabecera SQLite correcta) pero falla al restaurar o
   pierde filas. Es un fallo silencioso: se descubre cuando se necesita.

 Recomendación:
   Generar una instantánea consistente y servir esa copia temporal.

 Implementación sugerida (Node >= 22.16, sqlite.backup):

     import { backup } from "node:sqlite";
     const tmp = path.join(DB_DIR, `backup-${Date.now()}.db`);
     await backup(db, tmp);
     res.download(tmp, nombre, () => fs.unlink(tmp, () => {}));

   Implementación compatible con Node 22.13+ (VACUUM INTO):

     const tmp = path.join(DB_DIR, `backup-${Date.now()}.db`);
     db.exec(`VACUUM INTO '${tmp.replace(/'/g, "''")}'`);
     res.download(tmp, nombre, () => fs.unlink(tmp, () => {}));

   Añadir además:
     - PRAGMA integrity_check sobre la copia antes de enviarla.
     - Borrado garantizado del temporal (try/finally).
     - Cabecera Content-Length y nombre de archivo sin datos del sistema.

 M-03 · MEDIO · Fechas imposibles aceptadas y persistidas
--------------------------------------------------------------------------------
 Ubicación : website/backend/server.js:1894   (agenda)
             website/backend/server.js:2002   (crear reporte)
             website/backend/server.js:2034   (editar reporte)
 Tipo      : Validación de datos
 Estado    : CORREGIDO (04/11/2026). Ver 8.2.

 Descripción:
   La validación es solo la regex ^\d{4}-\d{2}-\d{2}$. Verificado:
     POST /api/agenda   {"fecha":"2027-02-31"} -> 201
     POST /api/reportes {"fecha":"2027-02-31"} -> 201

   Además, new Date("2027-02-31T00:00:00Z") se interpreta como el 3 de marzo,
   así que el cálculo de anticipación (server.js:1919-1922) usa una fecha
   distinta de la que se guarda.

 Impacto:
   Agenda con fechas inexistentes, ordenamientos erróneos y validaciones de
   anticipación que no coinciden con la fecha mostrada.

 Recomendación:

   function fechaISOValida(valor) {
     if (typeof valor !== "string" || !/^\d{4}-\d{2}-\d{2}$/.test(valor)) return false;
     const [a, m, d] = valor.split("-").map(Number);
     const f = new Date(Date.UTC(a, m - 1, d));
     return f.getUTCFullYear() === a && f.getUTCMonth() === m - 1 && f.getUTCDate() === d;
   }

   Usarla en agenda y reportes, y normalizar la fecha antes de guardar.

 M-04 · MEDIO · El contenido "datos" de un reporte no se valida y rompe la vista
--------------------------------------------------------------------------------
 Ubicación : website/backend/server.js:981-995
             website/public/js/reportes.js:445-478
 Tipo      : Validación / error de cliente
 Estado    : CORREGIDO (04/11/2026). Ver 8.3.

 Descripción:
   serializarDatos() solo comprueba que sea objeto y que no supere 256 KB.
   Verificado:
     POST /api/reportes {"tipo":"uso","datos":{"labels":null}} -> 201

   Luego buildReporteHTML() ejecuta rep.datos.labels.map(...) y
   rep.datos.fallas.map(...) sin comprobar existencia. El detalle del reporte
   lanza un TypeError y la vista queda vacía (y el CSV puede fallar igual).

 Impacto:
   Un reporte con datos incompletos inutiliza la pantalla; cualquiera con permiso
   de creación puede dejar registros "envenenados" para los administradores.

 Recomendación:
   Validar la forma por tipo en el backend y blindar el render con valores por
   defecto.

   function validarDatosReporte(tipo, datos) {
     const d = datos && typeof datos === "object" ? datos : {};
     if (tipo === "uso" || tipo === "disponibilidad") {
       const labels = Array.isArray(d.labels) ? d.labels.filter(x => typeof x === "string") : [];
       const valores = Array.isArray(d.valores) ? d.valores.filter(Number.isFinite) : [];
       if (labels.length !== valores.length) {
         const e = new Error("Datos del reporte inconsistentes"); e.status = 400; throw e;
       }
       return { labels, valores };
     }
     if (tipo === "fallas") {
       return { fallas: Array.isArray(d.fallas) ? d.fallas.slice(0, 500) : [] };
     }
     // inventario / otro
     return d;
   }

   En el cliente:
     const labels = Array.isArray(rep.datos?.labels) ? rep.datos.labels : [];
     const valores = Array.isArray(rep.datos?.valores) ? rep.datos.valores : [];
     const fallas = Array.isArray(rep.datos?.fallas) ? rep.datos.fallas : [];

 M-09 · MEDIO · El service worker cachea inventario filtrado por rol por URL
--------------------------------------------------------------------------------
 Ubicación : website/public/service-worker.js:9-13 y 116-135
             website/public/js/data.js:990-1003
 Tipo      : Exposición de datos entre sesiones

 Descripción:
   /api/laboratorios y /api/equipos devuelven campos distintos según esTecnico()
   (server.js:570-584: IP, MAC, serie, hardware). El service worker guarda la
   respuesta bajo la URL, sin usuario ni rol.

   Escenario en equipo compartido:
     1. Un técnico consulta equipos -> caché con IP/MAC/serie.
     2. La sesión caduca o se cierra el navegador (sin logout explícito).
     3. Otro usuario básico entra sin conexión -> recibe la copia del técnico.

 Impacto:
   Exposición de inventario técnico a un rol que no debería verlo. La caché solo
   se borra en el logout explícito.

 Recomendación:
   - Borrar API_CACHE al iniciar sesión y al detectar expiración de sesión.
   - Incluir usuario/rol en la clave de caché, o
   - No cachear respuestas autenticadas: cachear solo una vista pública sin
     campos técnicos (o dejar el offline solo para HTML/CSS/JS).

 Implementación sugerida (cliente, al login exitoso):

   navigator.serviceWorker?.controller?.postMessage({ type: "limpiar-cache-api" });

   Y en el service worker, además del mensaje, limpiar al recibir un 401:

   if (response.status === 401) caches.delete(API_CACHE);

 M-10 · MEDIO · La cabecera Permissions-Policy configurada no se emite
--------------------------------------------------------------------------------
 Ubicación : website/backend/server.js:169-177
 Tipo      : Configuración de seguridad inefectiva

 Descripción:
   Se pasa a Helmet una opción permissionsPolicy con un objeto anidado. Helmet
   7/8 no admite esa opción (verificado en los typings de helmet@7.1.0 y
   8.1.0), por lo que se ignora en silencio y la cabecera nunca se envía.

 Impacto:
   Se cree tener una política de permisos (cámara, micrófono, geolocalización,
   pago, USB) que en realidad no existe.

 Recomendación:

     app.use((req, res, next) => {

 M-12 · MEDIO · El logout puede no revocar el refresh token
--------------------------------------------------------------------------------
 Ubicación : website/public/js/data.js:990-1003
 Tipo      : Gestión de sesión

 Descripción:
   logout() lanza fetch(POST /logout) y navega inmediatamente a login.html. La
   navegación puede cancelar la petición antes de que el servidor la procese.
   El refresh token (30 días) queda válido aunque el usuario crea que cerró
   sesión.

 Impacto:
   En un equipo compartido o robado, la sesión sigue viva. El botón "Cerrar
   sesión" no cumple su promesa.

 Recomendación:

   async logout() {
     try {
       await fetch(`${API_BASE}/logout`, {
         method: "POST",
         headers: { "Content-Type": "application/json" },
         credentials: "same-origin",
         keepalive: true
       });
     } catch { /* sin red: se limpia igualmente el cliente */ }
     navigator.serviceWorker?.controller?.postMessage({ type: "limpiar-cache-api" });
     localStorage.removeItem("lc_sesion");
     window.location.href = "login.html";
   }

   keepalive permite que la petición sobreviva a la navegación. Alternativa:
   navigator.sendBeacon().

 6. RECOMENDACIONES TRANSVERSALES Y MEJORES IMPLEMENTACIONES
--------------------------------------------------------------------------------

 6.1 Seguridad de sesión
 -----------------------
   - Cookies: mantener HttpOnly + SameSite=lax + Secure en producción. Ya está.
   - Añadir un token CSRF explícito (double-submit) además de la comprobación de
     Origin. La comprobación actual es correcta, pero un token CSRF protege
     también si se relaja la política de Origin en el futuro.
   - Rotar el refresh token en cada uso (ya se hace) y mantener token_version
     por usuario para revocar todas las sesiones al cambiar contraseña o rol.
   - 2FA obligatorio para admin y nivel "total"; opcional para técnicos.

 6.2 Validación de entrada
 -------------------------
   - Unificar toda la validación en express-validator o en un esquema central.
   - Reglas mínimas por campo: tipo, longitud, rango, formato y pertenencia a
     catálogos (tipo de reporte, estado, rol, nivel).
   - Rechazar propiedades desconocidas en cuerpos sensibles (config, reportes)
     para evitar mass assignment accidental.
   - Validar fechas con componentes, no solo regex.

 6.3 Integridad de datos
 -----------------------
   - Calcular reportes en el backend; nunca generar datos en el cliente.
   - Guardar un campo "origen" o "demo" en reportes y mostrarlo en la UI/CSV.
   - Añadir claves foráneas que falten y comprobar PRAGMA foreign_key_check en
     mantenimiento.
   - Versionar el esquema y probar migraciones en una copia antes de producción.

 6.4 Respaldos y recuperación
 ----------------------------
   - Snapshot consistente (VACUUM INTO o sqlite.backup).
   - integrity_check antes de entregar y después de restaurar.
   - Probar la restauración periódicamente en un entorno de staging.
   - Conservar varios puntos en el tiempo (no solo la última copia) y cifrar si
     el respaldo sale del servidor.
   - Documentar RPO/RTO: con copia manual, el RPO depende de la última descarga.

   Niveles disponibles y decisión adoptada:

   +---------------------+--------------------------------+-----------+------------------+
   | Nivel               | Cubre                          | RPO       | Retención        |
   +---------------------+--------------------------------+-----------+------------------+
   | Descarga manual     | copia puntual y auditoría      | variable  | la que se guarde |
   | Backups del volumen | datos, corrupción y redeploy   | 24 h      | 6/27/89 días     |
   | Copia externa (R2)  | pérdida de volumen o proveedor | 24 h      | 90 días          |
   +---------------------+--------------------------------+-----------+------------------+

 6.4.1 Línea base adoptada: backups del volumen de Railway
 ---------------------------------------------------------
   Se adopta como primera capa el backup automático del volumen, porque no
   requiere código ni credenciales y cubre el riesgo más frecuente (corrupción
   o borrado accidental de datos dentro del volumen). Se activa en el panel:
     Servicio del backend → Settings → Backups → Daily + Weekly + Monthly.
   Railway conserva: diario 6 días, semanal 27 días y mensual 89 días.
   RPO: 24 h. RTO: minutos (restaurar y verificar).
   Coste: Railway factura los backups como almacenamiento incremental del
   volumen; con una base de pocos MB el importe es marginal, pero no es gratis.
   Disponibilidad por plan: el plan Free no incluye backups del volumen
   (maxBackupsCount = 0). Para activarlos hace falta un plan de pago que los
   incluya; mientras tanto, la copia disponible es la descarga manual desde
   Configuración → Respaldos.
   Límites: los backups viven en el mismo proyecto y proveedor. Borrar el
   volumen elimina también sus backups, y restaurar un punto descarta los
   backups más nuevos creados después de ese punto. No protegen contra el
   borrado del proyecto o de la cuenta, la suspensión de Railway ni una caída
   prolongada. Para eso existe la capa siguiente.

 6.4.2 Copia fuera del proveedor (opcional, pendiente)
 -----------------------------------------------------
   El respaldo descargable resuelve la consistencia, pero no la durabilidad: si
   se pierde el volumen (disco, instancia, cuenta de hosting), la única copia
   desaparece con él. Además de la línea base, hay dos opciones para copiar
   fuera del proveedor; la primera es la recomendada cuando se decida activarla.

   Opción A — snapshot programado + copia externa (recomendada a futuro)
     - Un cron, un servicio del sistema o el propio servidor (con
       `LC_BACKUP_AUTO=1`) ejecuta a diario:
         sqlite3 /ruta/labcontrol.db \
           "VACUUM INTO '/ruta/backups/labcontrol-$(date +%F).db'"
       o, desde la propia app, `crearCopiaConsistente()`.
     - Verifica la copia con `PRAGMA integrity_check`.
     - Súbela a S3/R2 (o a otra carpeta/equipo fuera del servidor) con
       retención de 7/30/90 días y cifrado en reposo.
     - Preparado en 8.3, NO activado: bucket R2 `labcontrol-backups/labcontrol/`,
       respaldo diario a las 02:15 de America/Santiago desde el propio servidor
       (`LC_BACKUP_AUTO=1`) y retención local de 30 días. La activación queda
       como tarea opcional en PENDIENTES.txt.
     - RPO: 24 h (o la frecuencia elegida). RTO: minutos.
     - Ventaja: no cambia el runtime ni el `journal_mode` actual.

   Opción B — WAL + Litestream (si se quiere RPO de segundos)
     - Cambiar a `PRAGMA journal_mode = WAL` y ejecutar Litestream como
       proceso aparte, replicando de forma continua a S3/R2.
     - Ventaja: replicación continua y recuperación a un punto en el tiempo.
     - Requisito: sistema de archivos local (no OneDrive ni SMB) y un solo
       escritor. En Windows/OneDrive el WAL deja archivos `-wal`/`-shm` y
       bloquea copias y restauraciones.

   Nota sobre `journal_mode=DELETE`:
     El código usa DELETE a propósito para evitar los bloqueos de Windows y
     OneDrive. Eso no impide la Opción A: `VACUUM INTO` funciona igual y produce
     una instantánea consistente. La Opción B sí exige mover la base a un
     volumen local (o a Linux/Railway) antes de activar WAL.

   En ambos casos:
     - Probar la restauración al menos una vez al trimestre.
     - No guardar la copia en la misma carpeta o volumen que la base.
     - Cifrar la copia si sale del servidor y limitar quién puede leerla.
     - Documentar RPO/RTO y la persona responsable del respaldo.

 6.4.3 Procedimiento de restauración (Railway)
 ---------------------------------------------
   Antes de restaurar, guarda el estado actual para no perder lo último:

     railway volume files download /app/data/labcontrol.db \
       ./labcontrol-antes-de-restaurar.db

   (Ajusta la ruta al volumen real; también sirve Configuración → Respaldos en
   la app.) Verifica la copia elegida antes de usarla:

     sqlite3 ./labcontrol-antes-de-restaurar.db "PRAGMA integrity_check;"

   Restauración desde un backup del volumen:

     1. Servicio del backend → Settings → Backups → elegir el punto → Restore.
     2. Revisar el volumen restaurado que Railway monta y confirmar Deploy.
     3. Comprobar /api/salud y abrir el panel con una cuenta admin.
     4. Ejecutar PRAGMA integrity_check sobre la base restaurada.
     5. Revisar usuarios, agenda y equipos (que no estén vacíos ni truncados).
     6. Anotar la fecha del punto restaurado y el motivo en el registro del
        establecimiento.

   Ten en cuenta que la restauración descarta los backups más nuevos que se
   hayan creado después del punto elegido y solo funciona en el mismo proyecto
   y entorno. Si necesitas conservar ese estado, descárgalo antes con
   `railway volume files download` o desde Configuración → Respaldos.

   Restauración desde una copia descargada (R2 o manual):

     1. Detener el servicio o dejarlo en mantenimiento.
     2. Reemplazar `labcontrol.db` en el volumen por la copia verificada.
     3. Arrancar, comprobar integridad y repetir los pasos 3 a 6 anteriores.
     4. Si algo falla, restaurar el archivo guardado en el primer paso.

   La prueba completa se hace en un servicio de staging, nunca en producción.
   Responsable sugerido: el administrador del sistema, con respaldo del
   encargado de informática del establecimiento.

     conocidas. Se ignora con `LC_SEED_DEMO=1` para no romper el desarrollo,

     `cuentasDemoPendientes: <n>`; el endpoint público sigue devolviendo solo
     `{ ok: true }`.

   Acción pendiente fuera del código: probar la credencial en la instancia real,
   rotarla si funciona, revocar sus refresh tokens y revisar la auditoría.

 A-01 · Reportes con datos reales (server.js, reportes.js)

   - `calcularDatosReporte()` obtiene los datos de las tablas:
       uso             → horas reservadas por laboratorio en el mes del reporte
                         (JOIN agenda); redondeo a un decimal.
       disponibilidad  → % de equipos activos por laboratorio (JOIN equipos),
                         con respaldo al estado del laboratorio en bases
                         antiguas sin inventario individual.
       fallas          → equipos en estado 'falla', con su descripción real.
       inventario      → conteo por estado sobre la tabla equipos, con respaldo
                         a la ficha del laboratorio si la tabla está vacía.
   - `POST /api/reportes` y `PATCH /api/reportes/:id` ignoran `datos` del cliente
     para esos cuatro tipos y recalculan el contenido. Editar un reporte no
     permite reinyectar cifras inventadas.
   - Se eliminó `generarDatosMock()` del cliente; al crear ya no se envían
     cifras. La vista tolera datos ausentes o malformados (arrays vacíos,
     valores no numéricos) y muestra un aviso en vez de romperse.
   - Los reportes de tipo "otro" conservan el contenido libre del cliente.

 A-02 · Respaldo consistente (db.js, server.js)

   - `crearCopiaConsistente()` usa `VACUUM INTO` en un archivo temporal oculto
     (`.labcontrol-temporal-respaldo-…`), ejecuta `PRAGMA integrity_check` sobre
     la copia y la borra si la verificación falla.
   - `GET /api/backups/exportar` sirve esa instantánea con `res.download()`
     (`dotfiles: "allow"`) y elimina el temporal siempre, con éxito o error.
     Si el proceso muere, `limpiarTemporales()` barre los restos al arrancar.
   - La respuesta conserva `Content-Type: application/octet-stream` y añade
     `Content-Length`; el nombre descargado no revela rutas del sistema.

 M-01 · Login con correo sin distinguir mayúsculas (server.js)

   - La auditoría de login fallido registra ahora el identificador ya
     normalizado.

 M-03 · Fechas reales (server.js)

     fecha con `Date.UTC` y comprueba año, mes y día. Rechaza `2027-02-31`,

 8.3 CORRECCIONES M-04 Y DURABILIDAD EXTERNA
--------------------------------------------------------------------------------

 M-04 · Datos de reporte saneados y render tolerante (server.js, reportes.js)

   - `serializarDatos()` sanea el contenido antes de guardarlo:
       * copia profunda con `limpiarDatosLibres()` (máximo 12 niveles);
       * descarta `__proto__`, `constructor` y `prototype` en cualquier nivel;
       * convierte números no finitos (NaN/Infinity) a `null`;
       * mantiene el tope de 256 KB serializados y devuelve 400 si se supera.
   - El render del cliente usa arrays vacíos y valores por defecto cuando
     `labels`, `valores` o `fallas` no son listas. Un reporte antiguo con datos
     incompletos muestra el aviso "sin datos" en lugar de un TypeError.
   - `repFromRow()` y la edición usan `parsearJSON()`: un registro con JSON
     corrupto se lee como `{}` o `[]` y se puede reparar. Antes, un solo
     registro corrupto tumbaba el listado o el detalle completo.
   - Los tipos calculados siguen regenerando su contenido desde las tablas
     (A-01); el tipo "otro" conserva el contenido libre, ya saneado. No se
     rechaza una forma libre concreta: se garantiza que ningún contenido pueda
     romper la vista ni contaminar el prototipo.

 DUR · Respaldo fuera del servidor

   - Nuevo `website/backend/scripts/respaldo-externo.mjs` y comando
     `npm run respaldo`:
       * `crearInstantanea()` usa `VACUUM INTO` (copia consistente aunque el

       * `verificarIntegridad()` ejecuta `PRAGMA integrity_check` antes de dar
         la copia por buena;

     primera revisión tras el arranque. Si la subida falla, deja
     `.ultimo-intento` y no reintenta hasta el día siguiente (una ejecución

     `LC_BACKUP_S3_REGION`, `AWS_ACCESS_KEY_ID` y `AWS_SECRET_ACCESS_KEY`.
